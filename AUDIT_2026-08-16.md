# Audit du 2026-08-16 — VocalMelody Studio

## Identification

- Projet : VocalMelody Studio
- Objet : audit de l'état du code, des tests, du build/CI et de la documentation au 2026-08-16
- Branche audité : `main`, commit `f1ffad3` (arbre Git propre, synchronisé avec `origin/main`)
- Statut de l'audit : **NON EXHAUSTIF** — audit statique (lecture intégrale des sources) complété par la suite de tests existante ; sans corpus hostile dynamique, sans tests Unicode, sans validation audio interactive
- Méthode : lecture des 35 fichiers C++/H, `ctest` Debug et Release (8/8), `clang-format --dry-run --Werror` (0 échec), inspection Git, analyse statique, et 4 audits ciblés (common+pitch, audio+frontend, app+tests, docs+CI) dont les constats ont été re-vérifiés contre le code et, pour le point le plus contesté, contre la source de JUCE 8.0.15 au commit épinglé

## Verdict global

**Projet sain et discipliné pour son stade (phase 2 en cours). Aucun constat critique démontré.** Les problèmes identifiés sont des trous de robustesse aux frontières (fichiers forgés, chemins Unicode, thread UI), pas des bugs de logique centrale. Deux corrections de robustesse sont confirmées et traitées dans la branche `fix/import-hardening-channels-unicode` : le plafond de canaux avant allocation et les chemins Unicode MP3/métadonnées.

## Limites de l'audit

- Audit **statique + suite de tests existante** (8 suites CTest). Les constats « allocation potentiellement gigantesque » (canaux × trames) et « MP3 CBR tronqué » sont des **bornes théoriques** ; ils ne sont pas démontrés par un test dynamique à la date de l'audit.
- Aucun test hostile dynamique, aucun test Unicode, aucun fuzzing, aucune validation audio interactive n'a été exécuté.
- Temps de la suite : CTest Debug 8/8 (~6 s), Release 8/8 (~11 s) dans l'environnement observé.

## Constats retirés ou reclassés après relecture

| Constat initial | Décision | Justification |
|---|---|---|
| Use-after-free de l'`AudioFormatManager` dans `MainComponent::loadFile` | **RETIRÉ** (faux positif) | Vérification contre la source de JUCE 8.0.15 au commit épinglé `91ad83ae…` : `AudioFormatReader` ne possède pas de membre `AudioFormat*` (constructeur `(InputStream*, const String& formatName)`, membre `String formatName`) et détient son propre flux. Le reader est autonome ; détruire le manager après `createReaderFor` ne laisse aucun pointeur pendant. | « Allocation ~7,8 To » (ÉLEVÉ) | **RECLASSÉ « potentiellement gigantesque »** | Borne théorique possible avec métadonnées forgées ; non démontrée par un test dynamique à la date de l'audit (C-01). |

## Points forts confirmés

1. Strong types exemplaires (validation à la construction, immuabilité, comparaison à trois voies) et encapsulation soignée (usines `create` → `std::optional`, `[[nodiscard]]`, `noexcept`).
2. Défense en profondeur de l'import : limites 1 Gio / 30 M trames / 100 M trames resamplées, calculs en `long double`, SHA-256 avant/après (anti-mutation), rejet d'un MP3 renommé `.wav`, `DecoderGuard` RAII, gestion minimp3 vérifiée contre sa source.
3. Resampleur sinc/Blackman polyphasé de qualité (normalisation aux bords, gardes `isfinite`) avec test de réponse fréquentielle comparatif.
4. Tests DSP exigeants et déterministes (8/8 Debug et Release), vecteur MP3 Layer III réel épinglé par SHA-256, fixtures WAV écrites octet par octet.
5. Documentation exemplaire : cohérence doc ↔ code vérifiée (versions, PR/commits, 8 tests, 35 fichiers formatés), journal append-only, registre de risques vivant, limites jamais masquées.

## Corrections appliquées (branche `fix/import-hardening-channels-unicode`)

- Plafond de canaux (≤ 64) et plafond total d'échantillons décodés avant toute allocation dans `decodeWithJuce`, avec tests sur en-têtes WAV forgés (C-01).
- Chemins Unicode : `mp3dec_ex_open_w` (Windows) pour le décodage MP3 et `std::filesystem::path` pour la sauvegarde des métadonnées, avec tests sur chemins accentués (C-02).

## Mise à jour post-mesures (2026-08-16)

Les constats C-01/C-02 ont été corrigés (PR #6, branche `fix/import-hardening-channels-unicode`) et C-05/C-06 ont été **mesurés** :

- **C-01 (plafonds de décodage)** : corrigé — `kMaxChannelCount = 64` et `kMaxDecodedSamples = 100 M` vérifiés avant allocation. Tests sur en-têtes WAV forgés (65, 65 535 canaux, plafond total) ; preuve rouge/vert effectuée.
- **C-02 (chemins Unicode)** : corrigé — `mp3dec_ex_open_w` (Windows) et `std::filesystem::path`. Tests sur chemins accentués MP3 et métadonnées ; preuve rouge/vert effectuée.
- **C-05 (aliasing) — confirmé et corrigé** : mesuré par sondes (48 kHz → 16 kHz : 8,5-10 kHz replié à -15/-35 dB ; 96 kHz → 16 kHz : -9,8 dB à 8,5 kHz). Correctif `phase2/resampler-anti-aliasing` : rayon 32 (67 taps) + marge 0.78 → 8,5 kHz à -80 dB (44,1/48 kHz) et -26 dB (96 kHz) ; `analysisVersion` 3 → 4. Contrepartie : coupure -6 dB à ~6,3 kHz (documentée dans `PERFORMANCES.md`). Tests permanents ajoutés sur la bande critique (rouge/vert vérifié).
- **C-06 (MP3 CBR tronqué) — confirmé et assumé** : un CBR coupé en fin de fichier se décode sans erreur (la fin tronquée est ignorée, `last_error == 0`). Décision : **accepté et documenté** comme invariant (`Mp3Decoder.h`), test de figeage ajouté ; aucune détection fiable n'est disponible au niveau du décodeur.
- **C-04 (raisons d'échec non remontées) — corrigé** (PR #8) : `AudioImportOutcome` + `enum ImportError` (9 causes distinguées), rejet `UnsupportedFormat` avant décodage pour les extensions inconnues/M4A, UI « Import impossible : <raison> », chaque test d'échec vérifie l'erreur précise. La correction a exposé un bug latent de test (fichier `.bin` non fermé → réellement vide → `EmptyFile`).

Ces mesures et décisions sont tracées dans `PERFORMANCES.md` (T-102.3) et `SUIVI_DEVELOPPEMENT.md`.
